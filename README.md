Welcome to the AI Powered Football Match Predictor repository! This README provides an extensive overview of a powerful set of Python scripts for football data analysis. These versatile scripts allow you to collect, filter, and analyze football match data, including statistics, market values, and performance metrics. Whether you're a data enthusiast, a sports analyst, or a football fan, this repository provides valuable tools to gain insights from football match data.

## Quick Start

The data pipeline has been rebuilt as a Python package. To run the whole thing:

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows;  source .venv/bin/activate on Unix
pip install -e ".[dev]"
python -m football.pipeline
```

This reads `matches_detailed_processed/`, writes everything under `data/`, and
prints a health report. It does not modify its own inputs.

Or run everything — data, features, evaluation, saved model — in one command:

```bash
python -m football.run_all
```

```bash
pytest                             # run the test suite (164 tests)
python -m football.data.audit      # re-print the health report
python -m football.features        # build the pre-match feature table
python -m football.train           # walk-forward evaluation vs baselines
python -m football.train --save --calibration
python -m football.predict --home "Arsenal" --away "Liverpool"
```

### Predicting a fixture

```
$ python -m football.predict --home Liverpool --away Chelsea

Liverpool  vs  Chelsea     2023-08-28

  home win   50.7%  ####################
  draw       21.7%  #########
  away win   27.6%  ###########

  most likely: home win

  home form (pts/game, last 5)   2.60
  away form (pts/game, last 5)   0.80
  home squad value (EUR m)       794.80
  away squad value (EUR m)       961.95
```

It warns when a team has no history, when the fixture is far past the training
window, and when crowd votes are absent (supply them with `--votes 45,61,26`).

Stages: `football.data.merge` → `football.data.filter` →
`football.marketvalue.clean` → `football.marketvalue.join`. Each runs
standalone, e.g. `python -m football.data.merge`.

The scripts documented below are the original implementations. They still work
as described, but the package above supersedes the merge, filter and market
value steps — see [Legacy code](#legacy-code).

## Project Structure

The project is organized into the following folders:

- **football**: The rebuilt pipeline package (merge, filter, market values, joins).
- **merged**: Contains merged CSV files.
- **marketValue**: Includes scripts and data related to market value extraction.
- **filter**: Contains scripts and data for filtering match data.
- **performance**: Includes scripts for performance analysis.
- **matches_detailed**: Contains raw match data.
- **matches_detailed_processed**: Contains processed match data with statistics and votes by users.
- **model**: Reserved for the machine learning model.
- **webScrapper**: Contains web scraping-related files.
- **data**: Generated by `football.pipeline`. Not version controlled.
- **tests**: Test suite for the pipeline package.

## Scripts Overview

### Data Collection

1. #### `getStats.py`
   - **Description**: Collects detailed football match statistics from a website using Selenium.
   - **Output**: Saves data as JSON and CSV files.
   - **Usage**: Provides raw statistical data for further analysis.

2. #### `football.py`
   - **Description**: Collects football match data, calculates win probabilities, and generates a performance dataset.
   - **Output**: Produces a dataset with win probabilities and other match-related details.
   - **Usage**: Analyze teams' performance and predict match outcomes.

### Data Filtering

3. #### `filter_data.py`
   - **Location**: `filter/filter_data.py`
   - **Description**: Filters football match data, categorizing competitions as cup, friendly, or league. Removes rows with incomplete data.
   - **Output**: A clean and structured dataset suitable for analysis.
   - **Usage**: Prepare data for performance analysis.

### Performance Analysis

4. #### `perfomance_data.py` — **removed**
   - Calculated win probabilities from market values and recent form with a
     hand-rolled sigmoid. Replaced by `football/features.py`, which computes
     form properly (its rolling window sorted by outcome string rather than
     date, and matched probabilities back by team and date only, so a team
     playing twice on one date got the wrong row).

### Market Value Extraction

5. #### `SaveData.py`
   - **Location**: `marketValue/SaveData.py`
   - **Description**: Reads JSON data and converts it into a CSV file.
   - **Output**: Converts JSON data into a CSV format for compatibility.
   - **Usage**: Prepare data for market value extraction.

6. #### `marketValue.py`
   - **Description**: Extracts market values of football teams using web scraping.
   - **Output**: Generates a CSV file with market values.
   - **Usage**: Collect market value data for football teams.

### Data Manipulation

7. #### `fix_the_price.py`
   - **Location**: `marketValue/fix_the_price.py`
   - **Description**: Fixes market value data by converting values to a uniform format and handling zero values.
   - **Output**: Updated market value data with uniform formatting.
   - **Usage**: Ensure consistency in market value data.

8. #### `filtered_to_mv.py`
   - **Location**: `marketValue/filtered_to_mv.py`
   - **Description**: Transfers market value data to the filtered dataset, linking teams with their market values.
   - **Output**: Merges filtered match data with market values.
   - **Usage**: Combine match data with market values for comprehensive analysis.

9. #### `AddMV_into_filter.py`
   - **Location**: `marketValue/AddMV_into_filter.py`
   - **Description**: Appends market values to the filtered dataset using team name matching.
   - **Output**: Updated filtered dataset with appended market values.
   - **Usage**: Enhance match data with market value information.

### Utility

10. #### `merge.py`
    - **Location**: `merged/merge.py`
    - **Description**: Combines every processed match CSV into a single file.
    - **Output**: `merged/merged_output_detailed.csv`.
    - **Usage**: Produce one dataset from the per-day scrapes.

## Machine Learning Model

### Training the Model

11. #### `train_seq.py`
    - **Location**: `model/train_seq.py`
    - **Description**: Builds and trains a neural network model to predict match outcomes based on selected features.
    - **Output**: Saves the trained model as an `.h5` file.
    - **Usage**: Train the model using football match data.

## Usage Instructions

1. Clone this repository to your local machine.
2. Install the required Python packages by running `pip install -r requirements.txt`.
3. Ensure you have a compatible web driver (e.g., GeckoDriver for Firefox) installed.
4. Run the scripts in the provided order to execute the entire data analysis pipeline.
5. Customize each script as needed by following the specific usage instructions in their respective sections.

The full collection order, end to end:

```
football.py -> getStats.py -> merge -> filter -> marketValue -> performance -> model
```

Steps 3 onward are now handled by `python -m football.pipeline`.

## Known Data Issues

- **938 of 3,919 teams (24%) have no usable market value.** Two causes: the old
  price parser mapped the suffix `b` but tested `endswith('b')`, so Transfermarkt's
  `"1.24bn"` failed to parse and every club worth €1bn or more was stored as zero
  (the table has a hard ceiling at 998, and Arsenal, Man City and PSG all sit at
  the placeholder); the rest are scrape misses. `python -m football.pipeline`
  writes the re-scrape list to `data/interim/market_value_rescrape_targets.csv`.
- **About a third of matches have no stats or votes** — 14,263 rows with empty
  `stats`, 13,773 with empty `votes`. These are kept as missing, not zero-filled.
- **Outcome balance** is 44.5% home / 24.8% draw / 30.8% away across 43,429
  matches, so always predicting a home win scores 44.5%. That is the baseline any
  model has to beat.

## Model

Features are strictly pre-match. `football/features.py` processes matches one
calendar day at a time: every match on day D is featurised against team
histories ending at D-1, and only then are day D's results folded in. Match
statistics still appear, but as rolling averages of each team's *previous*
matches. `tests/test_no_leakage.py` checks this independently — including that
appending future matches never changes a past row's features.

Evaluation is walk-forward: 15 folds, each training only on matches that
finished before its 14-day test window opens, after a 120-day warm-up.

| model | log loss | Brier | accuracy | ECE |
| --- | --- | --- | --- | --- |
| gradient boosting | **1.0143** | 0.6070 | **50.3%** | 0.007 |
| logistic regression | 1.0165 | 0.6087 | 50.1% | 0.004 |
| form only | 1.0358 | 0.6221 | 48.0% | 0.011 |
| votes only | 1.0397 | 0.6247 | 48.0% | 0.006 |
| market value only | 1.0544 | 0.6350 | 46.5% | 0.020 |
| baseline: class priors | 1.0684 | 0.6459 | 44.7% | 0.006 |
| baseline: always home | 7.6368 | 1.1055 | 44.7% | 0.553 |

29,971 out-of-sample matches. Log loss and Brier lead because what matters is
whether the probabilities are honest; accuracy on a 3-class imbalanced problem
hides too much. ECE is expected calibration error — the average gap between
stated confidence and observed accuracy.

### Calibration

`python -m football.train --calibration` writes `reports/reliability.png`.
Home-win and away-win probabilities trace the diagonal almost exactly, and ECE
is 0.007: when the model says 60%, it happens about 60% of the time.

**The model almost never predicts a draw**, and that is worth understanding
before it looks like a bug:

| outcome | actual | predicted as argmax | recall |
| --- | --- | --- | --- |
| home win | 44.7% | 68.6% | 80.2% |
| draw | 25.0% | 1.9% | 2.2% |
| away win | 30.3% | 29.5% | 45.8% |

Draw probability never exceeds 0.52 and mostly sits in 0.2–0.3, so the argmax
almost never lands on it — suppressing draws outright actually *raises*
accuracy, to 50.5%. This is not miscalibration: among matches given a 25% draw
chance, about 25% really are draws. Draws are simply never the modal outcome,
because they sit between two extremes rather than at the end of a continuum.
If you need to call draws specifically, use a probability threshold rather than
the argmax.

Two diagnostics worth keeping:

- `--no-votes` costs only 0.9pp accuracy (50.3% → 49.4%). If crowd votes were
  capturing post-match information, removing them would collapse the model
  rather than nudge it — so they look like a genuine, weak pre-match prior.
- `--eval-end 2023-05-31` gives 50.2%, essentially unchanged. The summer
  friendly season is not distorting the headline number.

50.3% against a 44.7% baseline is in the normal range for published football
models. Football outcomes are close to irreducibly noisy; results far above this
usually indicate leakage.

## The betting market beats this model

The single most important result here, stated plainly. On the 21,220
out-of-sample matches that carry betting odds:

| model | log loss | Brier | accuracy | ECE |
| --- | --- | --- | --- | --- |
| **odds only** | **0.9973** | 0.5961 | **50.9%** | 0.008 |
| gradient boosting (everything) | 1.0001 | 0.5978 | 50.7% | 0.004 |
| logistic regression | 1.0033 | 0.5985 | 50.7% | 0.011 |
| elo only | 1.0305 | 0.6181 | 48.0% | 0.025 |
| form only | 1.0465 | 0.6277 | 46.9% | 0.007 |
| market value only | 1.0763 | 0.6514 | 43.2% | 0.002 |
| baseline: class priors | 1.0763 | 0.6514 | 43.2% | 0.002 |

A logistic regression on three numbers copied off a bookmaker's website beats
the full model — Elo, rolling form, squad values, crowd votes, rolling match
statistics and a tuned gradient booster combined. Re-tuning the booster
specifically on this dataset narrowed the gap (1.0017 → 1.0001) but did not
close it.

This is not a bug and not a tuning failure. Closing odds already contain
everything the market knows — injuries, suspensions, lineups, weather, motivation
— none of which any feature in this repository can observe. Beating them is the
hard problem in football modelling, and most published attempts do not.

### Can we anticipate the line? No.

`python -m football.line_movement` asks the one question that could still yield
an edge from public data: opening odds are what you could actually have bet at,
so can our features, given only the opening price, beat the **closing** price?

```
opening price            log loss 1.0005
closing price            log loss 0.9973
value of the drift       +0.0032     ← the line does move toward the truth

closing line             log loss 0.9973
opening + our features   log loss 1.0037
difference               +0.0064  [+0.0040, +0.0089]   ← conclusively worse
```

The market learns something real between opening and kick-off (0.0032 of log
loss). We cannot predict what. The interval sits entirely on the wrong side of
zero, so this is not "inconclusive" — it is a clear negative.

The sanity check passes too: drift adds nothing once you already hold the
closing price (+0.0003, interval spanning zero), which is the arithmetic behaving
as it should.

### Data sources

Three sources, merged by `python -m football.sources.combine` into
**128,751 matches spanning 2012-03-02 to 2026-09-10, 67.6% carrying betting odds**.

| source | matches | span | odds | statistics |
| --- | --- | --- | --- | --- |
| football-data.co.uk (main) | 23,995 | 2023–2026 | opening + closing, totals, handicap | shots, cards, referee |
| football-data.co.uk (extra) | 63,056 | 2012–2026 | closing only | none |
| goal.com scrape | 41,700 | 2022–2023 | none | possession, shots, corners, fouls |

The extra-leagues dataset adds 16 countries the main files do not cover —
Argentina, Brazil, Japan, USA, Mexico, Russia, China, Poland, Romania and more —
in a different schema (`Home`/`Away`/`HG`/`AG` rather than
`HomeTeam`/`AwayTeam`/`FTHG`/`FTAG`), with one file per country covering every
season since 2012.

```bash
python -m football.sources.footballdata --seasons 2324 2425 2526 2627 --extra --fixtures
python -m football.sources.combine
```

**On merging team names across sources.** Merging two clubs that share a name
would fabricate a history that never happened, so this was measured before being
done: of 172 names appearing in more than one source, 154 are the same club in
the same country, and the remaining 18 are country-label variants
(`Republic of Ireland`/`Ireland`, `China PR`/`China`) rather than genuine
collisions. No extra-league team name appears in two countries. `Arsenal` and
`Arsenal Sarandi` stay separate because normalisation does not strip the
distinguishing word.

`clubelo.com` was evaluated as a fourth source for calibrated cross-league Elo
ratings, but its API returned HTTP 502 on every endpoint tried.

### Many models: which kind helps

Running several models is right in one form and wrong in another, and both were
measured on the combined 66,956-match dataset (`python -m football.ensemble`).

**Routing by regime works.** The dataset contains two situations that want
opposite things — ~24,000 matches where a betting market exists and the market
is unbeatable, and ~43,000 where none exists and a model is all there is. A
router that picks the right specialist per match beats a single model trying to
serve both:

| model | regime | log loss | accuracy | n |
| --- | --- | --- | --- | --- |
| market | market priced | **0.9965** | **50.9%** | 23,519 |
| strength | market priced | 1.0252 | 48.5% | 23,519 |
| strength | no market | **1.0071** | **50.8%** | 30,009 |
| **router** | all matches | **1.0024** | **50.8%** | 53,528 |
| strength alone | all matches | 1.0151 | 49.7% | 53,528 |
| stack | all matches | 1.0104 | 50.4% | 53,528 |

**Stacking on the same target hurts.** A meta-learner over both specialists
scores 1.0150 where the market exists, against 0.9965 for the market alone — it
dilutes a sharp signal by mixing in a weaker one. Blending models that see the
same information is how a good signal gets averaged away.

Before this, a single estimator handled both regimes with `DropAllNaNColumns`
quietly discarding the odds columns on every early fold. That worked, but spent
the model's capacity learning a compromise between two incompatible situations.

### Every feature family, measured against the market

`python -m football.ablation` scores each family as *odds + family* against
*odds alone*, with a paired bootstrap interval — because on 21,220 matches a
gain of 0.002 is inside the noise, and reading it as real is how feature sets
fill up with junk.

| family | cols | delta | 95% interval | verdict |
| --- | --- | --- | --- | --- |
| elo | 4 | +0.0003 | [−0.0004, +0.0009] | no evidence |
| match stats | 8 | +0.0006 | [+0.0002, +0.0011] | no evidence |
| form | 16 | +0.0011 | [+0.0004, +0.0018] | no evidence |
| schedule | 4 | +0.0034 | [+0.0017, +0.0054] | no evidence |
| referee | 2 | +0.0002 | [−0.0003, +0.0007] | no evidence |

Nothing helps; several actively hurt. `everything` (1.0039) is worse than
`odds only` (0.9972).

Market value and crowd votes show exactly 0.0000 because those columns are
**absent** from this dataset — they were not tested here, not disproved.

What follows from it:

- Treat odds as the benchmark, not a feature among others. Any new feature
  should be judged on whether it adds signal **on top of** odds.
- The model still earns its place where odds are unavailable: lower divisions,
  youth and women's competitions, and the 249 goal.com competitions
  football-data.co.uk does not cover.
- If a future version does beat the closing line consistently on held-out data,
  check for leakage first. That result is rare enough to be suspicious.

## Collecting new data

```bash
python -m football.scrape.goal --check              # are the selectors still valid?
python -m football.scrape.transfermarkt --check     # what still needs a value?
python -m football.scrape.transfermarkt --limit 50  # fill the biggest gaps
python -m football.scrape.goal --start 2023-09-01 --end 2023-09-30
```

### football-data.co.uk (recommended)

The goal.com scrape stops at 2023-08-27 and its selectors are long dead. For
anything current, use this instead — static CSVs, free for personal use,
refreshed several times a week:

```bash
python -m football.sources.footballdata --seasons 2324 2425 2526 2627 --fixtures
python -m football.sources.combine                     # merge with the goal.com history
python -m football.train --dataset data/processed/matches_combined.csv --save
python -m football.predict --fixtures --dataset data/processed/matches_combined.csv
```

That last command scores every upcoming fixture and writes
`data/processed/fixture_predictions.csv`.

It supplies 23,995 matches from 2023-07-28 onward across 22 leagues, **all with
betting odds**, plus a weekly fixtures file for matches not yet played. Compared
with the scrape it also adds shots on target, cards, half-time scores and the
referee.

The two sources name clubs differently (`Man Utd` / `Man United`,
`Beşiktaş` / `Besiktas`), so `combine` bridges them through
`football.teams.normalise` — but only on **unambiguous** 1:1 matches. That guard
is load-bearing: `normalise` strips bare years, so `CSKA 1948` and `CSKA` both
reduce to `cska` despite being different clubs. Ambiguous keys are left
unbridged and listed in `data/interim/source_team_bridge.csv`.

Coverage is the trade-off: 22 leagues against the scrape's 271 competitions.

### goal.com scrape (legacy)

**Run `--check` first.** The selectors are hashed CSS-module class names
captured in 2023 (`row_row__UQmGm`), regenerated on every frontend deploy, so
they have very likely stopped matching. `--check` loads one page and reports
which ones still find anything, rather than letting a full run quietly produce a
directory of empty CSVs. They live in
[`football/scrape/selectors.json`](football/scrape/selectors.json) so they can
be repaired without touching Python.

What changed from `webScrapper/`:

- **Rate limiting and robots.txt**, on by default. The original requested as
  fast as Selenium allowed and handled the resulting 403s by writing zeros.
- **Failures are counted and reported by reason** instead of becoming `"N/A"`.
  A third of the dataset has no statistics and there is no record of why.
- **Selenium 4 API.** `executable_path=` and `options.headless` were both
  removed in Selenium 4.3; the originals raise immediately on any current
  version.
- **No duplicated work.** The original ran the same URL list forwards and
  backwards in two threads, and its "already fetched" check looked in the wrong
  directory, so nothing was ever skipped.
- **`extract_stats` collects every group.** The original returned from inside
  its category loop, which is why `Total shots` and `Ball possession` appear in
  half as many rows as `Fouls` and `Corners`.
- **Re-scraping never overwrites its input.** Results go to a separate file and
  are merged explicitly; the original rewrote `teams_market_value.csv` in place
  every run, which is how the raw scraped strings were lost for good.

Both sites prohibit automated collection in their terms of service. The polite
defaults here reduce load; they do not grant permission.

## Legacy code

Superseded by the `football` package, kept until the rebuild is verified:
`merged/merge.py`, `filter/filter_data.py`, `marketValue/fix_the_price.py`,
`marketValue/AddMV_into_filter.py`, `marketValue/filtered_to_mv.py`,
`marketValue/SaveData.py`.

CartPole, then evaluated it on football data) and `performance/perfomance_data.py`.

`model/train_seq.py`, `train_func.py` and `predict.py` are superseded by
`football/train.py` but kept for reference until Phase 5 lands a working
prediction CLI.

`webScrapper/` and `marketValue/marketValue.py` remain the only way to collect
new data. Their CSS selectors are hashed build artefacts (`row_row__UQmGm`) and
have likely stopped matching the live sites.
